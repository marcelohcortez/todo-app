## 1. Critical Security Issues

### 1.1 Account deletion — no ownership check
**File:** `backend/app/api/account/delete/route.ts`

`DELETE` removes any account whose cookie is valid — no `userId` comparison. If someone guesses another user's JWT, they can delete that account.

**Fix:** Compare the authenticated `user._id` against the `userId` query param before calling `deleteUser()`:
```ts
if (String(user._id) !== userId) {
  return unauthorized("You can only delete your own account");
}
```

### 1.2 No brute-force protection on account deletion
**File:** `backend/app/api/account/delete/route.ts`

The rate limiter exists (`rateLimitMiddleware`) but **no route applies it**. Account deletion is unrestricted.

**Fix:** Wrap the handler with the rate limiter (5 attempts / 15 min):
```ts
import { rateLimitMiddleware } from "@/lib/rateLimit";
export const POST = rateLimitMiddleware(
  { windowMs: 15 * 60 * 1000, max: 5 },
  async (req) => { /* existing handler */ }
);
```

### 1.3 `bcryptjs` in frontend `package.json` is unnecessary
**File:** `frontend/package.json`

`"bcryptjs": "^3.0.3"` is a server-side password hashing library. Including it in the frontend bundle wastes ~200 KB (pre-hash) and leaks crypto primitives into client-side code.

**Fix:** Remove `"bcryptjs": "^3.0.3"` from `frontend/package.json`.

### 1.4 No CSRF protection on cookie-based auth
**File:** All backend API routes

The app uses JWT stored in an HTTP-only cookie. Browsers automatically attach cookies to any request from the same origin. An attacker hosting a malicious page on the same origin (e.g. a compromised sub-domain or a local dev setup) could craft a CSRF-style request.

**Fix:** Add SameSite=Strict to the cookie or use a double-submit token pattern:
```ts
// In setCookie (auth.ts):
res.setHeader("Set-Cookie", `${cookieName}=${token}; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=${30 * 24 * 60 * 60}`);
```
For dev environments, also allow `SameSite=Lax` when `NODE_ENV !== "production"`.

### 1.5 OAuth connection revocation — no re-authentication required
**File:** `backend/app/api/oauth/connections/[clientId]/route.ts`

A malicious actor who gains access to a logged-in session can disconnect any connected OAuth app without the user re-entering their password. This is acceptable for convenience but may not meet security-sensitive requirements.

**Status:** Informational — low severity for a personal task manager.

### 1.6 MCP token — no expiration policy
**File:** `backend/lib/mcp.ts` + `backend/app/api/mcp-token/` routes

MCP tokens have **no expiry**. Once created, they are valid forever unless manually revoked. Users with many AI clients accumulate long-lived tokens.

**Fix:** Add an optional `expiresIn` field (default 90 days) and a background cron to purge expired tokens:
```ts
const tokenData = {
  id: crypto.randomUUID(),
  label,
  token,
  userId: user._id,
  createdAt: new Date(),
  // Add:
  expiresAt: new Date(Date.now() + (expiresInMs ?? 90 * 24 * 60 * 60 * 1000)),
};
```

## 2. Bugs & Runtime Issues

### 2.1 Frontend service worker file missing
**File:** `frontend/components/ServiceWorkerRegister.tsx` references `sw.js`, but `frontend/sw.js` does not exist on disk.

The service worker registration will fail silently (browser console error: "Failed to register or update service worker: URL scheme must be secure").

**Fix:** Create `frontend/sw.js` with at minimum an empty `install` and `fetch` handler, or remove the `ServiceWorkerRegister` component if PWA is not required.

```js
// frontend/sw.js
self.addEventListener("install", () => self.skipWaiting());
self.addEventListener("activate", (e) => {
  e.waitUntil(clients.claim());
});
self.addEventListener("fetch", () => {});
```

### 2.2 `bcryptjs` version mismatch between backend and frontend
**File:** `backend/package.json` → `"bcryptjs": "^2.4.3"`
**File:** `frontend/package.json` → `"bcryptjs": "^3.0.3"` (should not be in frontend at all)

The major version mismatch (`2.x` vs `3.x`) can cause subtle behavioral differences in password hashing if both are ever used server-side in different deployment contexts.

**Fix:** Remove from frontend; keep `2.4.3` in backend for consistency.

### 2.3 Race condition in `useLiveRefresh`
**File:** `frontend/components/useLiveRefresh.ts`

`useEffect` schedules `setInterval` but doesn't clear it if the callback changes rapidly (e.g. user navigates away then back quickly). This can cause multiple intervals to run simultaneously, triggering redundant API calls.

**Fix:** Store the interval ID in a ref and clear it on unmount/change:
```ts
export function useLiveRefresh(callback: () => void, intervalMs?: number) {
  const savedCallback = useRef(callback);
  savedCallback.current = callback;

  useEffect(() => {
    const id = setInterval(() => savedCallback.current(), intervalMs);
    return () => clearInterval(id);
  }, [intervalMs]);
}
```

### 2.4 `tasks` `useMemo` missing `boards` dependency
**File:** `frontend/components/TaskApp.tsx`, line ~100

```ts
const tasks = useMemo(() => {
  const boardIds = boards.filter(b => b.active).map(b => b._id);
  // ...
}, [tasks, boards.filter(...)]);
```

The `useMemo` depends on `boards` but `boards` is not in the dependency array (or it uses a derived value that isn't memoized). This causes stale board filtering after board updates.

**Fix:** Ensure the dependency array includes `[tasks, boards]` or compute the active board IDs outside `useMemo` as a separate `useMemo`.

### 2.5 Dead code in `SearchBar.tsx`
**File:** `frontend/components/SearchBar.tsx`

Lines 19-22 contain a commented-out `onFocus` handler that was left as a TODO. This is not a bug per se but dead code that should be removed to keep the file clean.

### 2.6 `MicButton.tsx` uses deprecated `webkitSpeechRecognition`
**File:** `frontend/components/MicButton.tsx`

The component uses `new (window as any).webkitSpeechRecognition()` which is deprecated in favor of `SpeechRecognition`. It also lacks error handling for permission-denied or network-failure cases, which will silently do nothing in production.

**Fix:** Use the standard API with fallback and error handling:
```ts
const SpeechRecognition = (window as any).SpeechRecognition || (window as any).webkitSpeechRecognition;
if (!SpeechRecognition) {
  setError("Speech recognition is not supported in this browser");
  return;
}
// Add: recognition.onerror callback
```

## 3. Code Smells & Architectural Concerns

### 3.1 In-memory rate limiter doesn't scale
**File:** `backend/lib/rateLimit.ts`

Rate limit counters are stored in a `Map` in each Node.js worker process. On any deployment with more than one worker (Vercel, PM2, Docker scaling), each instance has its own counter, effectively multiplying the allowed request rate.

**Fix:** Use a shared store (Redis) or a database-backed rate limiter. For now, with Vercel's single-worker free tier, this is acceptable but document the limitation.

### 3.2 In-memory LRU cache has no TTL expiry
**File:** `backend/lib/cache.ts`

The cache is an LRU map with a `max` size but no time-based expiry on individual entries. Items stay until evicted by size, which means stale data (e.g. OAuth tokens, user lists) can persist indefinitely.

**Fix:** Add a per-entry `expiresAt` timestamp and skip/evict expired entries on access:
```ts
const now = Date.now();
if (entry.expiresAt && now > entry.expiresAt) {
  cache.delete(key);
  return null;
}
```

### 3.3 JWT secret never rotated
**File:** `backend/lib/auth.ts`

The `AUTH_SECRET` is read once from env and used for all JWT signing. There is no key rotation mechanism, meaning every user's session is valid until the secret changes or the 30-day cookie expires.

**Fix:** Add a `keyId` field to the JWT header and support multiple secrets. Periodically rotate the active secret and let old tokens expire naturally.

### 3.4 Password policy is minimal
**File:** `backend/lib/password.ts`

Only checks `password.length >= 8`. No complexity requirements (uppercase, lowercase, number, special char), no check against common passwords, and no minimum/maximum length bounds beyond 8.

**Fix:** Add a minimum of 12 characters and optionally check against a list of common passwords (e.g., `zxcvbn` library):
```ts
if (password.length < 12) return "Password must be at least 12 characters";
```

### 3.5 No input validation library
**File:** All API routes

User input is validated manually with `if/else` and `typeof` checks. There's no structured validation library (e.g., `zod`, `joi`). This makes validation logic inconsistent across routes and hard to maintain.

**Fix:** Introduce `zod` for request body validation:
```ts
import { z } from "zod";

const CreateUserSchema = z.object({
  email: z.string().email(),
  password: z.string().min(8),
});

// In route:
const body = CreateUserSchema.parse(req.body);
```

### 3.6 MongoDB connection error handling is incomplete
**File:** `backend/lib/mongodb.ts`

The `connect()` function logs errors but `db` remains `null` on failure. Subsequent routes calling `getDb()` will hit `TypeError: Cannot read properties of null` when accessing `.collection()`.

**Fix:** Return an error response when DB is unavailable:
```ts
export function getDb(): Promise<mongodb.Db> {
  const db = getDbSync();
  if (!db) {
    throw new Error("Database connection failed. Please try again later.");
  }
  return db;
}
```

### 3.7 No API response schema consistency
**File:** Multiple API routes

Some routes return `{ success: true, ... }`, others return `{ data: { ... } }`, and others return raw objects. There's no unified response envelope.

**Fix:** Standardize on a single shape:
```ts
interface ApiResponse<T> {
  success: boolean;
  data?: T;
  error?: string;
}
```

### 3.8 `bcryptjs` comparison in `password.ts` — timing-safe
**File:** `backend/lib/password.ts`

Uses `bcrypt.compare()` which is timing-safe. ✅ Good practice noted.

### 3.9 Frontend components have large file sizes
- `TaskApp.tsx`: ~22 KB — mixes state management, data fetching, UI rendering, and drag-and-drop logic
- `NotesApp.tsx`: ~13 KB — similar mixing of concerns
- `Nav.tsx`: ~9 KB — navigation + options menu logic combined
- `SharedPage.tsx`: ~21 KB — shared content + personal content in one component

**Fix:** Split large components into smaller, focused components:
- `TaskApp.tsx` → `TaskList.tsx` + `TaskItem.tsx` + `TaskBoardView.tsx`
- `Nav.tsx` → `NavDesktop.tsx` + `NavMobile.tsx` + `OptionsMenu.tsx` (already separated for options)

### 3.10 Duplicate API route structure
**File:** `backend/app/api/account/*` vs `backend/app/api/*`

There are **two** sets of routes for friends, shares, and notifications:
- `/api/friends/*` (standalone)
- `/api/account/friends/*` (account-scoped)
- `/api/shares/*` (standalone)
- `/api/account/shares/*` (account-scoped)
- `/api/notifications/*` (standalone)
- `/api/account/notifications/*` (account-scoped)

This duplication increases maintenance burden and may confuse users of the API.

**Fix:** Consolidate under `/api/account/*` for user-scoped resources and remove the standalone routes, or vice versa.

## 4. JavaScript Bundle Optimization

### 4.1 No Next.js `experimental_*` bundle optimizations
**File:** `backend/next.config.mjs` + `frontend/next.config.mjs`

Both config files have minimal settings. Modern Next.js 14+ offers several bundle-reducing options:

**Fix (frontend):**
```js
const nextConfig = {
  // ...existing config...

  // Enable tree-shaking for better dead code elimination
  optimizePackageImports: ['@tailus/themer', 'clsx', 'pusher-js'],

  // Enable React Fast Refresh (already default in dev, but be explicit)
  reactStrictMode: true,
};
```

### 4.2 `@tailus/themer` is an unused dependency
**File:** `frontend/package.json`

`"@tailus/themer": "^0.1.8"` is a design-tool CLI, not a runtime library. It should not be in `dependencies`. If it's used in development only, it belongs in `devDependencies`. If unused at all, remove it.

**Fix:** Move to `devDependencies` or remove entirely.

### 4.3 No `transpilePackages` for shared code
**File:** `frontend/next.config.mjs`

If any shared library code exists between backend and frontend, it won't be tree-shaken by default.

**Fix:** If there's shared code, configure:
```js
transpilePackages: ['shared-lib'],
```

### 4.4 No dynamic imports for heavy components
**File:** Multiple pages

Heavy components like `TaskApp.tsx` (~22 KB) and `NotesApp.tsx` (~13 KB) are imported at the top level on every page load, even when navigating between routes. This prevents code splitting.

**Fix:** Use `next/dynamic` for route-level code splitting:
```tsx
import dynamic from "next/dynamic";

const TaskApp = dynamic(() => import("@/components/TaskApp"), {
  loading: () => <p>Loading…</p>,
  ssr: false, // if it uses browser-only APIs
});
```

### 4.5 Pusher SDK loaded on all pages
**File:** `frontend/components/ServiceWorkerRegister.tsx` + other components

The Pusher SDK (`pusher-js`) is bundled into the main chunk even for pages that don't use real-time features (login, settings, etc.).

**Fix:** Dynamic import Pusher only where needed:
```ts
const Pusher = await import("pusher-js");
```

### 4.6 No `assetPrefix` / `basePath` for CDN delivery
**File:** `frontend/next.config.mjs`

Static assets (CSS, JS bundles) are served from the same origin as the app. There's no CDN configuration.

**Fix:** If using a CDN, configure:
```js
const nextConfig = {
  assetPrefix: process.env.NEXT_PUBLIC_CDN_URL || "",
  // ...
};
```

### 4.7 Missing `next.config.mjs` `swcMinify` explicit setting
**File:** Both config files

Next.js 14+ uses SWC minification by default, but it's worth being explicit for clarity.

### 4.8 Frontend `globals.css` has no Purge/Tailwind content optimization
**File:** `frontend/tailwind.config.ts`

Tailwind CSS v3 should automatically purge unused classes, but the `content` array should explicitly include all template paths to ensure proper tree-shaking in production builds.

**Fix:** Ensure `tailwind.config.ts` has comprehensive content paths:
```ts
content: [
  "./app/**/*.{ts,tsx}",
  "./components/**/*.{ts,tsx}",
  "./lib/**/*.{ts,tsx}",
],
```

## 5. Missing Best Practices

### 5.1 No TypeScript strict mode enforcement
**File:** `backend/tsconfig.json` + `frontend/tsconfig.json`

Both configs appear to use default `tsconfig.json` settings. Strict mode (`strict: true`) should be enabled for full type safety.

**Fix:** Add to both `tsconfig.json`:
```json
{
  "compilerOptions": {
    "strict": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "exactOptionalPropertyTypes": true
  }
}
```

### 5.2 No API documentation
The API has no OpenAPI/Swagger spec. For an app with OAuth, MCP, and sharing endpoints, documenting the interface is important for third-party integrations.

**Fix:** Use `swagger-autogen` or `tsoa` to auto-generate OpenAPI docs from the route handlers.

### 5.3 No environment variable validation at startup
**File:** Both `next.config.mjs` files

The frontend config throws on missing `BACKEND_URL`, but the backend does not validate required env vars (`MONGODB_URI`, `AUTH_SECRET`, `PUSHER_SECRET`) at startup.

**Fix:** Add validation to `backend/lib/mongodb.ts` or `backend/app/api/auth/login/route.ts`:
```ts
if (!process.env.MONGODB_URI) throw new Error("MONGODB_URI is not set");
if (!process.env.AUTH_SECRET) throw new Error("AUTH_SECRET is not set");
```

### 5.4 No health check endpoint
**File:** Backend

There's no `/api/health` or similar endpoint for load balancers, Docker health checks, or monitoring.

**Fix:** Add `backend/app/api/health/route.ts`:
```ts
import { NextResponse } from "next/server";
export async function GET() {
  return NextResponse.json({ status: "ok", timestamp: new Date().toISOString() });
}
```

### 5.5 No structured logging
**File:** All backend files

Logging uses plain `console.log` and `console.error` with no structured format (JSON), no log levels, and no correlation IDs. This makes debugging in production difficult.

**Fix:** Introduce a simple structured logger:
```ts
function log(level: string, msg: string, meta?: Record<string, unknown>) {
  console.log(JSON.stringify({ level, msg, timestamp: new Date().toISOString(), ...meta }));
}
```

### 5.6 No test coverage for core business logic
**File:** `backend/lib/tasks.ts`, `backend/lib/boards.ts`, etc.

The `test` script runs `vitest run` but there's no indication of tests for core logic (auth, password hashing, pagination, etc.).

**Fix:** Add tests for:
- `lib/auth.ts` — JWT creation and validation
- `lib/password.ts` — hashing and comparison
- `lib/pagination.ts` — offset/limit calculations
- `lib/search.ts` — query builder logic

### 5.7 No error boundary in frontend
**File:** `frontend/app/layout.tsx`

There's no React Error Boundary to catch rendering errors in client components. A crash in `TaskApp.tsx` would show a blank page.

**Fix:** Add an error boundary component:
```tsx
// frontend/components/ErrorBoundary.tsx
export class ErrorBoundary extends React.Component {
  state = { hasError: false };
  static getDerivedStateFromError() { return { hasError: true }; }
  render() {
    if (this.state.hasError) return <p className="text-danger-300">Something went wrong. <button onClick={() => window.location.reload()}>Reload</button></p>;
    return this.props.children;
  }
}
```
Wrap the main app in `frontend/app/page.tsx` with `<ErrorBoundary>`.

### 5.8 Missing `robots.txt` and `sitemap.xml`
**File:** Frontend

For SEO (if the app is public-facing), these are important. The landing page (`/`) benefits from proper meta tags.

**Fix:** Add `frontend/app/robots.ts` and `frontend/app/sitemap.ts` (Next.js 14+ route handlers).
